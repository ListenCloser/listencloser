# ADR-001 — One Persistent Project Workspace

Status: accepted
Date: 2026-07-28
Owners: orchestrator

## Context

The current app uses session-scoped browser state (localStorage/sessionStorage) with no persistent project concept. Users lose context on refresh or across sessions. Workspace layout, active artifacts, workflows in progress, and UI state are all ephemeral. There is no named aggregate that groups related works, artifacts, versions, and workspace state together.

## Decision

Every user interaction lives inside a named persistent project. A project owns works, artifacts, versions, workflows, and workspace layout state. Opening the app restores the last active project. Multiple projects are supported but only one is active at a time. Projects are user-scoped: auth scopes all project data.

## Invariants affected

- Projects own access and workspace state.
- Auth scopes all project data.
- One project is active at any time per user session.
- Switching projects preserves independent workspace state for each project.

## Alternatives considered

- **Multi-session workspace without explicit projects**: Let workspace state be stored per URL or per browser tab. Rejected because there is no named, shareable identity and no way to group artifacts across sessions.
- **Pages-based navigation (current pattern)**: Let each feature manage its own state independently. Rejected because state loss on refresh and inability to restore composite workspace layout.
- **File-system-only persistence**: Store workspace state entirely in server-side files. Rejected because it ties workspace state to a specific storage backend and makes multi-device sync harder.

## Consequences

- Requires a user-owned `projects` table in the database.
- Auth integration must scope all project queries by the authenticated user.
- Workspace restoration logic must be added to app bootstrap.
- Current `localStorage`/`sessionStorage` state must be migrated into the project persistence layer.
- Enables future features: project sharing, project exports, workspace snapshots.

## Migration

1. Add `projects` table with fields: `id`, `user_id`, `name`, `workspace_state` (JSONB), `last_active_at`, `created_at`, `updated_at`.
2. Backfill from existing `localStorage`/`sessionStorage` for signed-in users: create a default project per user populated with current state.
3. Implement dual-read during transition: on app load, read from both old browser store and new project API. If new API has data, prefer it; otherwise fall back to browser store.
4. Once all reads go through the project API, remove dual-read and delete the old browser store paths.

## Rollback

Old browser storage remains readable during the dual-read phase. If the project API fails, the app falls back to `localStorage`/`sessionStorage`. Removing the API call and reverting to browser-only storage is a configuration change. No data loss: existing browser state is never deleted during migration.

## Validation

- Workspace state survives page refresh: all panels, selections, and active artifacts restore to their previous positions.
- Project switching preserves independent state: switching from Project A to Project B and back restores Project A's exact workspace layout.
- New user onboarding creates a default project automatically.

## Supersedes / superseded by

- Supersedes implicit session-scoped state management in the reference implementation.
- Superseded by: none.
