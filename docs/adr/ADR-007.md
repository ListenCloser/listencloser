# ADR-007 — Migration: Reference Model to Domain Model

Status: accepted
Date: 2026-07-28
Owners: orchestrator

## Context

The current repository uses a `LibFile`-centric data model with session-scoped state, synchronous processing in the request path, and tab-based page-per-feature navigation. ADRs 001-006 define the target domain architecture: Projects, Works, Artifacts, Versions, Entities, Insights, Alignments, and asynchronous Jobs with capability contracts. This ADR defines the migration path from the reference implementation to the domain model without regressing existing behavior.

## Decision

New domain tables and APIs are introduced alongside existing storage. Both backends operate simultaneously during transition. The migration proceeds in vertical slices per ADR-006: add new tables, backfill existing data, move readers first, move writers, delete old paths.

### Migration sequence

1. **Add new tables alongside old storage (dual-write).** New domain tables (`projects`, `works`, `artifacts`, `versions`, `entities`, `insights`, `alignments`, `jobs`, `capabilities`) coexist with existing `tracks`, `models`, `jobs` tables and storage buckets.
2. **Backfill existing user data when new tables are created.** `LibFile` records map to Artifacts and initial Versions. Inline analysis fields map to Entities and Insights. Existing audio files remain in storage, referenced by new Artifact records.
3. **Register existing outputs as Versions.** Each `LibFile` row with a storage path becomes an Artifact with one Version. Transcriptions and analysis outputs become additional Versions of their parent Artifact.
4. **Move frontend readers first, then writers.** Update read paths to prefer new tables, falling back to old storage when data is not yet migrated. New data is written to both old and new storage during transition, then exclusively to new storage.
5. **Remove obsolete JSON fields and public storage policies last.** Once all consumers read from new storage and no writes go to old storage, remove `LibFile` compatibility adapters, drop old tables, and retire public storage buckets.
6. **Removal condition for each compatibility layer:** all clients must have been migrated for 30 days with zero reads against old storage paths.

### Compatibility layers

- `LibFile` → `Artifact` + `Version` adapter: maps `library/` storage paths to Artifact UUIDs and initial Versions.
- `LibFile.analysis` → `Entity` + `Insight` adapter: maps inline JSON analysis fields to structured Entity and Insight rows.
- Tab-based Studio → `/workspace` shell adapter: routes existing URLs to workspace modes during transition.
- Sync handler → Job adapter: wraps synchronous `POST /music/transcribe` in a Job envelope with status polling.

### Rollback

Old code paths remain intact until cutover is verified. If a new API or table causes issues, readers fall back to the old storage path. Old `LibFile`-based endpoints continue to function independently. Migration can be paused or reversed at any stage by routing back to old paths.

### Validation

- Existing E2E tests continue to pass during migration.
- New tests validate domain model behavior independently.
- A migration dashboard tracks read/write percentages against new storage, pending compatibility adapters, and removal status.
- User-facing behavior is identical before and after each migration step.

## Alternatives considered

- **Big-bang migration**: Drop old tables and rewrite all paths at once. Rejected — too risky for a live application with user data.
- **Parallel codebase**: Build domain model in a separate repo or branch, then merge. Rejected — duplicates effort and delays feedback.
- **No migration**: Leave old model in place indefinitely. Rejected — violates ADRs 001-006 and blocks future architectural milestones.

## Consequences

- Dual storage backends coexist during migration. Increased operational complexity mitigated by vertical slice sequencing and explicit removal conditions.
- Compatibility adapters add indirection. Each adapter carries a documented 30-day removal condition after all clients migrate.
- New features are built against domain contracts, not against `LibFile` abstractions.
- Vestigial prototype tables (`tracks`, `models`, `jobs` from MusicGen prototype) are dropped once all references are removed.
- Public storage buckets (`audio`, `datasets`, `adapters`) are retired in favor of private buckets with RLS enforcement.
