# ADR-006 — Current App is Reference Implementation, Not Architectural Truth

Status: accepted
Date: 2026-07-28
Owners: orchestrator

## Context

The current repository (`chat-agent-rebased` branch) implements a working Music AI Studio with transcription, analysis, library management, and chat functionality. However, it uses a tab-based page-per-feature pattern, a `LibFile`-centric data model, session-scoped state, and synchronous processing in the request path. These patterns are implementation accidents of the prototype phase — pragmatic choices made to ship fast, not architectural decisions intended for the long-term product.

## Decision

The existing codebase is preserved as a working reference implementation. It demonstrates correct end-to-end behavior and serves as the functional baseline. Changes must preserve existing behavior until its replacement is verified against the same behavior. New architecture — domain contracts, workspace shell, durable background jobs, structured entities and insights, capability abstractions — is introduced alongside the existing app through compatibility layers, not as a big-bang rewrite. The architecture ADRs (this bundle) take precedence over current implementation patterns when there is a conflict.

## Invariants affected

- Architecture SOT (this ADR bundle) > reference implementation patterns.
- Existing working behavior must be preserved during migration. No regression in functionality.
- Compatibility layers (adapters mapping old patterns to new contracts) have explicit removal conditions and timelines.
- New features are built against the target architecture, not against the reference implementation patterns.
- Reference implementation code is only modified to fix critical bugs or to wire into compatibility layers.

## Alternatives considered

- **Big-bang rewrite**: Discard the current codebase and rebuild from scratch against the target architecture. Rejected because it halts delivery, risks regressions, and loses the working knowledge embedded in the current implementation.
- **Freeze reference, build new in parallel**: Stop all changes to the current app, build the new architecture in a separate codebase, then cut over. Rejected because it delays incremental value delivery and creates a long feedback gap.
- **Evolve reference implementation organically**: Gradually refactor the current codebase toward the target architecture without explicit compatibility layers. Rejected because without clear boundaries, the refactor can stall halfway and leave the codebase in an inconsistent state.

## Consequences

- Dual architecture exists during migration: old `LibFile` model, session-scoped state, and synchronous handlers coexist with new domain entities, workspace store, and durable job system.
- Compatibility adapters map old `LibFile` records to new Artifact/Version/Entity/Insight domain contracts.
- Increased codebase complexity during transition. Mitigated by vertical slice migration (migrate one feature end-to-end before starting the next) and clear removal criteria for each compatibility layer.
- Every compatibility layer includes a documented removal condition (e.g., "Remove when all reads go through Artifact API") and a scheduled removal review date.
- The reference implementation is not frozen — it can receive bug fixes, but feature work targets the new architecture.

## Migration

1. Add new tables and APIs alongside existing storage. Both old and new storage backends operate simultaneously.
2. Backfill existing data: `LibFile` records map to Artifacts and initial Versions. Inline analysis maps to Entities and Insights.
3. Move readers first: update read paths to prefer new tables, falling back to old storage when data is not yet migrated.
4. Move writers: new data is written to both old and new storage during transition, then exclusively to new storage.
5. Delete old paths: once all consumers read from new storage and no writes go to old storage, remove compatibility adapters and drop old tables.
6. Repeat per vertical slice (transcription, analysis, library, chat).

## Rollback

Old code paths remain intact until cutover is verified. If a new API or table causes issues, readers fall back to the old storage path. Old `LibFile`-based endpoints continue to function independently. The migration can be paused or reversed at any stage by routing back to old paths.

## Validation

- Existing E2E tests continue to pass during migration. The test suite gates any change that breaks existing behavior.
- New tests validate domain model behavior independently: Artifact versioning, Entity/Insight queries, Transport/Selection synchronization, Capability adapter correctness.
- A migration dashboard tracks: percentage of reads served from new storage, percentage of writes going to new storage, number of pending compatibility adapters, and removal status of each.
- User-facing behavior is identical before and after each migration step.

## Supersedes / superseded by

- Supersedes implicit assumptions that the reference implementation's patterns (tab-based pages, `LibFile` model, session-scoped state, synchronous processing) represent intentional architectural choices.
- Superseded by: none.
