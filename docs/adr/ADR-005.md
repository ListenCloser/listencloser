# ADR-005 — Workflows Depend on Capabilities, Not Implementations

Status: accepted
Date: 2026-07-28
Owners: orchestrator

## Context

The current app calls Basic Pitch, music21, FluidSynth, and ffmpeg directly in the request path (`music_features.py`, `analyze.py`). Route handlers import and invoke specific libraries. There is no abstraction between "transcribe audio" (the intent) and the specific library performing transcription (the implementation). Replacing Basic Pitch with another transcription model would require changes across route handlers, frontend expectations, test fixtures, and error handling — a high-risk cross-cutting change.

## Decision

Workflows (understand, correct, compare, create, export) express user intent and orchestrate capabilities. Capabilities are stable, versioned interfaces that declare: accepted inputs, produced outputs, implementation version, parameters with schemas, quality/confidence ranges, known failure modes, and provenance metadata. Implementations (Basic Pitch, music21, FluidSynth, ffmpeg) live behind capability adapters. Workflow code never imports a specific OSS library directly — it depends on capability contracts.

## Invariants affected

- Workflows depend on capabilities, not implementations.
- Every capability declares its contract (inputs, outputs, version, parameters, quality/confidence, failure modes, provenance).
- Implementations are replaceable behind stable interfaces without changing workflow code.
- A capability may have multiple implementations (e.g., multiple transcription models). The active implementation is a configuration choice.
- Capability adapters are responsible for translating between the capability contract and the implementation's native interface.

## Alternatives considered

- **Direct library calls with dependency injection**: Inject library instances into workflow functions. Rejected because the interface is still tied to the library's API shape; swapping implementations requires matching parameter and return types.
- **Plugin system with dynamic discovery**: Allow implementations to register themselves via a plugin architecture. Rejected as over-engineering for the current scale; a straightforward adapter pattern with explicit configuration is sufficient and easier to reason about.
- **Microservice per capability**: Run each capability as a separate service. Rejected for now due to operational overhead; adapters can be extracted to services later if scaling demands it.

## Consequences

- Requires capability interfaces defined in Python as protocols or abstract base classes (e.g., `TranscriptionCapability`, `SynthesisCapability`, `AnalysisCapability`, `ExportCapability`).
- Requires adapter classes for each current library: `BasicPitchAdapter`, `Music21Adapter`, `FluidSynthAdapter`, `FFmpegAdapter`.
- Adds one layer of indirection between workflow code and libraries. Increases code volume but isolates change.
- Enables benchmarking implementations against each other (same input, compare outputs and performance).
- Enables A/B testing of implementations without changing workflow logic.
- Configuration determines which implementation is active for each capability.

## Migration

1. Define capability interfaces as Python `Protocol` classes with typed inputs and outputs.
2. Wrap each existing library call in an adapter class implementing the corresponding capability protocol.
3. Update workflow code to accept capabilities as dependencies (constructor injection or registry lookup) instead of importing libraries directly.
4. Existing endpoints continue to work through adapters — no behavior change from the user's perspective.
5. Add configuration mechanism for selecting active implementations per capability.

## Rollback

Direct library calls continue to work; adapters are additive. If an adapter is broken or misconfigured, the old direct import path can be restored by changing a single import in the workflow module. No data migration is required.

## Validation

- Swapping Basic Pitch for a different transcription model requires only creating a new adapter implementing `TranscriptionCapability` and updating configuration. No workflow code, route handler, or frontend code changes.
- Running the same audio through two transcription adapters produces comparable outputs (same format, different values).
- All existing E2E tests pass when routed through adapters with the original implementations.
- A capability's contract is stable: changing an implementation's internal logic does not break downstream consumers.

## Supersedes / superseded by

- Supersedes direct library imports in route handlers and analysis modules in the reference implementation.
- Superseded by: none.
