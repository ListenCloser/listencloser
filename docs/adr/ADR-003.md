# ADR-003 — Immutable Artifact Versions with Lineage

Status: accepted
Date: 2026-07-28
Owners: orchestrator

## Context

The current app mutates transcription data in place: saving corrections overwrites the original transcription JSON. There is no version history, no way to compare corrections to the original, and no chain of provenance from raw audio to final polished output. Users cannot trace how an artifact was derived, revert to a previous state, or audit which job produced a given version.

## Decision

Every artifact version is immutable. Version chains form explicit lineage via parent-child relationships (`parent_version_id`). Originals are never overwritten; every transformation, correction, or generation creates a new version. Versions reference the job that produced them, capturing who, when, and how the version was created. The version chain is a directed acyclic graph rooted at the original artifact.

## Invariants affected

- Versions are immutable once created.
- Lineage is explicit: every version has a parent (except originals).
- Every version has provenance: `created_by` (user or system), `job_id` (the processing job that produced it), `created_at`.
- Originals (version 1 of any artifact) are never modified or deleted through normal application flow.
- Deleting or archiving an artifact must consider all downstream versions.

## Alternatives considered

- **Mutable artifacts with audit log**: Keep a single artifact record and log changes in an audit table. Rejected because reconstructing any previous state requires replaying the audit log, and the audit log can become inconsistent with the artifact.
- **Snapshot-based versioning with full copies**: Store a full copy of each version without lineage. Rejected because lineage is needed for provenance, diffing, and understanding derivation chains.
- **Event-sourced artifact state**: Artifact state is a projection of events. Rejected because added complexity for a domain where versions are the natural unit of interaction.

## Consequences

- Requires `artifact_versions` table with: `id`, `artifact_id`, `parent_version_id`, `job_id`, `data` (immutable payload), `created_by`, `created_at`.
- Every mutation becomes an append (INSERT, never UPDATE on version data).
- Storage costs increase proportionally with version count. Offset by future deduplication and retention policies.
- Frontend must display version history and allow comparison between versions.
- Jobs must declare their output as new versions, not in-place updates.
- Old `saveTranscription` pattern must be replaced with version creation.

## Migration

1. Backfill existing transcription data as initial versions (version 1) with no parent.
2. Link version 1 to a synthetic "migration" job for provenance.
3. New processing creates new versions via the version creation API.
4. Replace old `saveTranscription` calls with version creation calls.
5. Display version history in the UI once the table is populated.

## Rollback

Old storage paths remain readable for existing data. The old `saveTranscription` function can be called directly if version creation is bypassed. Version table can be dropped without data loss if no new versions have been created.

## Validation

- Transcription correction creates a new version with `parent_version_id` pointing to the corrected version. Both versions are independently retrievable.
- Attempting to UPDATE an existing version's data fails or is rejected by the API.
- Every version in the chain is retrievable: fetching an artifact returns the full version DAG.
- Comparing two versions shows the diff between their data payloads.
- Deleting the original version fails or warns if downstream versions exist.

## Supersedes / superseded by

- Supersedes in-place mutation of transcription data in the reference implementation.
- Superseded by: none.
